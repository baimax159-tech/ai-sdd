# P1 需求获取引擎

## 宿主适配

文中的 `${PLUGIN_ROOT}` 指插件根目录：Claude Code 使用 `${CLAUDE_PLUGIN_ROOT}`；Codex 从当前 skill 目录向上定位插件根目录后使用其绝对路径。文中的 `Skill("...")` 表示调用宿主的技能能力：Claude Code 使用该原生调用，Codex 使用已安装技能的等效调用；若无直接调用能力，则将所需技能规范读入当前上下文后继续。

## 触发条件

当用户表达以下意图时使用本 skill：
- "做 XXX" / "新增 XXX" / "开发 XXX" → 新功能路径
- "迁移" / "重构" / "替换" / "兼容" / "对齐" / "差异分析" → 迁移路径
- 混合（既有迁移又有新功能）→ 先迁移固化基线，再补新增

## Phase A: 意图识别

1. 从用户输入判断路径（新功能 or 迁移），告知用户判断结果并确认
2. 创建契约文件：
   - 新功能：`node ${PLUGIN_ROOT}/scripts/sdd.mjs scaffold P1 <name>`
   - 迁移：`node ${PLUGIN_ROOT}/scripts/sdd.mjs scaffold P1p <name>`
3. **开发能力就绪检查**（若本次 session 已运行过 P0 则跳过此步）：
   - 通过项目特征文件（`go.mod`/`pom.xml`/`package.json` 等）识别主语言
   - 快速检查核心覆盖：
     - **Skill**：session 的 system-reminder available skills 中是否覆盖核心实践维度（testing、error-handling、design-patterns、security、coding-standards）
     - **MCP**：codegraph（`codegraph_*` 工具是否可用）、context7（`context7_*` 工具是否可用）
   - 若有明显缺失（Skill 核心维度缺失 ≥2 项，或 codegraph/context7 不可用），向用户提示：
     > "检测到当前项目缺少 N 项开发能力（skill/MCP），可能影响后续阶段质量。建议先运行 P0 完整检查，还是跳过继续？"
   - 用 `宿主原生交互工具` 提供选项：`运行 P0 完整检查` / `跳过，继续 P1`
   - 用户选择运行 P0 → 调用 `Skill("sdd-p0")`，完成后回到 P1 继续
   - 用户选择跳过 → 正常继续
4. **探测构建/测试/运行命令**：契约创建后运行 `node ${PLUGIN_ROOT}/scripts/sdd.mjs detect-commands <name>`，
   从项目标记文件（`go.mod`/`pom.xml`/`package.json`/`Cargo.toml`/`pyproject.toml` 等）推断 build/test/run 命令并写入 `state.json`。
   这些命令供 P2「验证命令锚点」、P4「验证命令」直接复用，避免各阶段现场猜命令。探测不到的语言留空，由后续阶段人工补。

**上下文聚焦**：意图识别与基础设施准备完毕。本阶段所有判断和产出以用户在本 session 中明确表述的需求为唯一信息基准，不依赖对话历史中的隐含假设；模糊项必须追问，禁止静默脑补。

## Phase B-1: 新功能路径 — 多轮追问

### 元素清单

以下 10 个元素，每个必须有明确确认点。不得静默假设任何一个：

| # | 元素 | 追问方式 | 缺失行为 |
|---|---|---|---|
| 1 | 角色与权限 | "涉及哪些角色？各角色能做什么？" | 必须追问 |
| 2 | 主流程 | "核心正常路径是什么？步骤？" | 必须追问 |
| 3 | 分支流程 | "有没有可选/条件路径？" | 必须追问 |
| 4 | 异常与边界 | "失败了怎么办？极值？空值？" | 必须追问 |
| 5 | 并发 | "会有并发/竞态吗？" | 不适用则确认原因 |
| 6 | 兼容性 | "需要兼容旧版本/多平台吗？" | 不适用则确认原因 |
| 7 | 安全 | "认证/授权/数据保护有要求吗？" | 不适用则确认原因 |
| 8 | 数据模型 | "输入是什么？输出？状态变化？" | 必须追问 |
| 9 | NFR | "性能/可用性有具体指标吗？" | 追问确认有无 |
| 10 | 技术约束 | "有必须遵守的技术限制吗？" | 可选 |

### 追问策略

**Round 1（信息提取）**：
- 从用户原始描述中提取已知元素
- 展示："我理解到：[已知]。还需要确认：[缺失项，≤3 个问题]"

**Round 2（深化补盲）**：
- 根据 Round 1 答案推断反向场景
- 追问边界/异常/安全
- 提出假设让用户确认："我假设 XXX，对吗？"

**Round 3（收敛）**：
- 展示完整场景地图草案
- 标注所有待澄清项
- 问："还有遗漏吗？没有的话我生成契约草案"

**上限 5 轮**。超出 → 剩余项列入"待澄清问题"，不再追问。

### 应对用户描述能力有限

| 用户表现 | skill 行为 |
|---|---|
| 只说一句话 | 从中推断场景，给 2-3 个选项让用户选 |
| 回答模糊 | 给具体选项："你是指 A 还是 B？" |
| 说"不知道" | 提供行业常见做法："通常做法是 X，要用这个吗？" |
| 遗漏安全/并发 | 主动提："这个场景可能有 [问题]，需要处理吗？" |
| 答非所问 | 重新组织问题，更具体化 |

## Phase B0: 需求最大化覆盖（描述能力弱的用户友好）

### 手段① subagent 并行场景扩展
初步采集后，按需求复杂度规划并派发 subagent，从不同视角反向生成「用户大概率漏掉」的候选场景/候选 AC：
- subagent-A: 边界/异常/极值/空值候选
- subagent-B: 安全/认证/授权/注入候选
- subagent-C: 并发/竞态/幂等候选
- subagent-D: 兼容/角色权限/多端候选
合并去重后，向用户逐条做三态 triage：**要 / 不要 / 改**。用户只做选择题，不必从零描述。
（简单需求可跳过扩展并说明原因。）

### 手段② 结构化覆盖自审清单（出 gate 前强制）
对 10 元素 + 场景维度逐项给结论，每项必须「有内容」或「显式不适用 + 原因」：
| 维度 | 结论 |
|---|---|
| 角色权限 / 主流程 / 分支 / 异常边界 / 并发 / 兼容 / 安全 / 数据模型 / NFR / 技术约束 | 有内容 / 不适用+原因 |
任一维度留空 → 不得进入 gate。

### 手段③ 示例/选项式追问（铁律）
所有追问必须给具体选项 / 行业常见做法 / 类比，**禁止开放式空问**。
反例（禁止）："你要什么权限模型？"
正例："常见是 A)仅本人可见 B)团队共享 C)公开，你选哪个？还是别的？"

## Phase B-2: 迁移路径 — 代码扫描 + 差异确认

### Step 1: 确定扫描范围

追问："要迁移/重构的模块是哪些？给路径或模块名。"

### Step 2: 代码扫描

用 subagent 并行扫描每个模块，提取：
- 接口签名（方法名、参数、返回值）
- 数据模型（字段、类型、约束）
- 依赖关系（上下游调用）
- 错误码和异常处理
- 配置项

**工具选择（按优先级，优先用 CodeGraph）**：

| 提取目标 | CodeGraph 工具 | 退化方案（CodeGraph 不可用时） |
|---|---|---|
| 模块文件结构 | `codegraph_files`（指定 path） | `Glob` 扫描目录 |
| 接口/类/函数定义 | `codegraph_search`（按 kind 过滤） | `Grep` 正则匹配签名 |
| 完整签名和源码 | `codegraph_node`（includeCode=true） | `Read` 目标文件 |
| 调用关系（谁调它） | `codegraph_callers` | 手动 Grep 引用 |
| 调用关系（它调谁） | `codegraph_callees` | 手动阅读函数体 |
| 模块整体上下文 | `codegraph_context`（描述任务） | 多次 Read + Grep |
| 深度探索陌生模块 | `codegraph_explore`（传符号名） | 逐文件 Read |

**扫描流程**：
1. 先用 `codegraph_files` 确认模块文件清单
2. 用 `codegraph_context` 获取模块整体结构（入口点、关键符号）
3. 对关键接口用 `codegraph_node` 获取完整签名
4. 用 `codegraph_callers`/`codegraph_callees` 梳理依赖关系
5. 仅对 CodeGraph 未索引的内容（配置文件、错误码常量）退化为 Read/Grep

### Step 3: 展示扫描结果让用户确认

```
"我扫描到模块 X 有以下行为：
 - [接口列表]
 - [数据模型]
 - [错误处理]
 请确认是否准确，有无遗漏或错误。"
```

用户修正 → 更新行为基线。

### Step 4: 逐项追问差异意图

- "哪些行为必须保持不变？" → 行为一致性白名单
- "哪些要改变？改成什么？" → 差异清单 DF-XX
- "A 和 B 冲突时怎么处理？" → 合并规则
- "有新增行为吗？" → 如有，提示后续补 P1-req
- **验收环境可达性（必问，决定 P4 验证口径）** → 用 `宿主原生交互工具` 问"验收时你能提供哪些对照物？①可运行的旧实现（作为逐项对照的 oracle） ②等价的输入/依赖/数据 ③旧实现的真实输入输出样本（录制/日志/快照）"：
  - 有可运行旧实现 + 等价输入 → 验证口径 = 与旧实现逐项 oracle 对照
  - 只有部分（如仅样本、或仅部分依赖）→ 验证口径 = 已固化样本 golden 比对 + 可达部分对照
  - 都不可达 → 验证口径**降级**为 golden 样本 + 结构/契约级校验，并显式标注"无 oracle，不承诺逐项一致"
  结论写入契约的行为一致性声明，供 P4 直接锚定，避免挂无法验证的一致性承诺

### Step 5: 生成 P1p-diff 契约

填充：对比对象、差异清单（DF-XX + 处理策略）、合并规则、行为一致性声明。需人工决策项标注。

## Phase C: 共同出口

两条路径汇合后：

1. **生成契约草案** — 按模板填充
2. **术语识别** — 提取新术语展示给用户确认
3. **出口自检 loop（≤3 轮）** — 跑闸门，红则按报告修复后重跑：
   `node ${PLUGIN_ROOT}/scripts/sdd.mjs gate SDD/contracts/<name>/<file>.md`
4. **人工确认** — gate 绿后展示契约摘要，停下等用户明确说"进入 P2"/"可以"。不得自动推进。
   确认后运行 `node ${PLUGIN_ROOT}/scripts/sdd.mjs state-set <name> P1 confirmed true` 落盘确认状态（P2 的 can-enter 据此放行）。
5. **术语登记** — 确认的新术语追加到 `SDD/glossary.md`
6. **引导下一步** — "P1 已确认，是否开始 P2 架构设计？"

## 硬约束

1. **不得静默脑补** — 不确定的维度必须追问
2. **不得跳过元素** — 10 个元素每个必须确认（即使确认为"不适用"）
3. **不得自动推进** — gate 未绿不得请求用户确认
4. **扫描结果必须用户确认** — 不能直接采信
5. **追问上限 5 轮** — 超出强制收敛
6. **每轮最多 3 个问题** — 不堆问题轰炸用户
7. **追问必须选项式交互** — 禁止开放式空问；必须使用宿主原生交互工具或等效选项 UI，禁止在纯文本里列 A/B/C/D 让用户手打
8. **覆盖自审有空项不得进 gate**
9. **迁移类必须问验收环境可达性** — Step 4 必须确认用户能提供的验收环境，据此定 P4 验证口径，禁止挂无法验证的一致性承诺
