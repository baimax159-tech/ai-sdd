# P3 实现派发引擎

## 触发条件

- P2 已经用户确认
- 用 `node ${CLAUDE_PLUGIN_ROOT}/scripts/sdd.mjs scaffold P3 <name>` 生成 P3 契约
- 用户确认开始实现

## Phase A: 加载执行上下文

0. **前置硬闸**：运行 `node ${CLAUDE_PLUGIN_ROOT}/scripts/sdd.mjs can-enter <name> P3`。
   非 0 退出（P2 gate 未绿或未经用户确认）则拒绝进入，提示用户先完成并确认 P2，不得继续。
1. 读取 P2 契约的完整内容：
   - 接口签名（方法名、参数、返回值）
   - 数据模型（字段、类型、约束）
   - 模块层划分（目录结构、依赖方向）
   - ADR 决策（技术选型、设计模式）
   - 通用抽象（扩展点接口定义）
2. 读取 P1/P1p 契约的 AC/DF/NFR 条目
3. 从当前 session 的 available skills 列表中识别实现相关 skill：
   - Claude Code 启动时已将所有已安装 skill（含软链、插件仓库）注册到 session
   - 遍历 system-reminder 中所有 available skills 的名称和 description
   - 结合 P2 契约已确定的技术栈（语言、框架），判断每个 skill 是否与当前项目的编码实现相关
   - **判断依据**：skill 的 description 涉及编码规范、测试、错误处理、安全、性能、并发等实现层面的内容，且与当前项目技术栈匹配
   - 将筛选出的 skill 名称记录为 **subagent 强制触发清单**，在 Phase D 的 subagent prompt 中以明确的 `Skill` 工具调用指令传递
4. 确认每个 P2 IU 都在执行计划中有对应 Task

**上下文聚焦**：契约文件已加载完毕。本阶段所有判断和产出以上方契约文件的明文内容为唯一信息基准，不依赖对话历史中的隐含假设或推断。遇到模糊或信息缺失，以契约文件为准；契约未覆盖的事项用 AskUserQuestion 向用户确认。

---

## Phase B0: Subagent 类型设计

基于 P2 IU 清单，在生成 Task 协议前先分析 subagent 工作模式：

1. **按工作性质对 IU 分类**（按项目实际情况确定，以下为示例分类）：
   - 数据层：数据模型定义、存储操作
   - 业务层：业务逻辑、服务编排
   - 接口层：路由、请求/响应处理
   - 基础设施层：配置、中间件、工具函数

2. **为每类设计可复用 prompt 框架**：
   - 每类 agent 对应统一的接口约束格式 + 实现协议格式 + 完成标准
   - 新增同类 IU 时，套用同一框架填写，不需重新设计整个 prompt

3. **扩展机制**：
   - 当出现新工作类型时，定义新分类 + 新 prompt 框架
   - 不修改已有分类的 prompt 结构，保持已有 agent 设计的稳定性

用 `AskUserQuestion` 展示分类方案 → 用户确认 → 进入 Phase B 按分类生成具体 Task 协议

---

## Phase B: 生成可执行 Task 协议

**每个 Task 不是一行任务描述，而是一份完整的实现协议。**

### Task 协议模板

每个 Task-XX 必须包含以下 5 个部分：

#### ① P2 接口约束
从 P2 契约中提取该 Task 涉及的：
- 接口签名（完整方法签名，含参数和返回值类型）
- 依赖的数据模型（结构体/字段定义）
- 关联的 ADR 决策（必须遵守的技术选型）
- 扩展点接口（如适用，须实现的接口协议）

#### ② 实现协议
该 Task 的核心实现思路：
- 关键算法/逻辑描述（不是"实现 XXX"，而是具体怎么做）
- 关键数据流（输入 → 处理 → 输出的具体路径）
- 错误处理策略（哪些错误、怎么处理）
- 与其他模块的交互方式（调谁、被谁调、通过什么接口）

#### ③ 测试策略
- 正向用例（输入 → 预期输出，至少 2 个）
- 边界用例（空值、极值、异常输入）
- 回归用例（P1p 行为一致性断言，如适用）
- 测试方法（单测/集成/mock 策略）

#### ④ 产物清单
- file: 目标文件路径
- test: 测试文件路径
- 依赖的前序 Task

#### ⑤ 完成标准
- 构建通过 + 测试全绿
- 代码与 P2 接口签名完全一致
- 注释规范：
  - 每个公开方法/函数必须有头部注释（说明功能、参数、返回值含义）
  - 复杂逻辑块（超过 10 行或含算法）必须有行内注释
  - 注释只写 WHY（隐含约束、业务规则、绕过特定问题的原因），不写 WHAT
  - 禁止废话注释（如 "// 返回结果"、"// 赋值"）
- 遵守项目编码规范

### 生成策略

- 简单 Task（纯数据模型/配置）：实现协议可精简，但接口约束和测试策略不可省
- 复杂 Task（含算法/编排/并发）：实现协议必须详细到伪代码级别
- 每个 Task 协议生成后写入契约 → 用户确认

## Phase C: 执行编排

对所有 Task 按依赖关系分 Stage，判断并行性：

```
规则:
- 目标文件无交叉 + 无依赖关系 → 可并行
- 有文件交叉 或 有依赖 → 必须串行
- 依赖不明确 → 按串行处理（安全优先）
```

形态选择是 AI 的规划职责：
- 多个无交叉无依赖 Task → 原生 subagent 并行组
- 强相关/共享文件 → 单 agent 串行，说明退化原因
- 大型独立子系统 → 可成组派发（agent 组）

展示 Stage 编排 → 用户确认 → 建议用户开启自动模式 → 进入派发。

> **自动模式引导**：Stage 编排确认后，向用户提示：
> "实现阶段（派发 → 验证 → 复核）将自动执行，预计耗时较长。建议开启自动接受模式（Shift+Tab 切换权限模式到 Auto-accept）让我持续工作，完成后我会停下等你确认。"
> 用户开启自动接受后，Phase D → E → F 连续执行不中断，直到 Phase G 停下等用户确认。

## Phase D: 派发 subagent 执行

### subagent 上下文

每个 subagent 收到：
1. 该 Task 的完整协议（接口约束 + 实现协议 + 测试策略 + 完成标准）
2. 已完成的前序 Task 产物（接口定义文件，供 import 使用）
3. **强制触发的 skill 调用指令**（Phase A 步骤 3 筛选的 skill 清单）

### subagent prompt 中的 skill 触发模板

subagent prompt **必须**包含如下格式的明确指令（skill 名称由 Phase A 步骤 3 筛选结果决定，按项目实际技术栈填入）：

```
在开始实现之前，你必须依次调用以下 Skill：
- 调用 Skill("<lang>-code-style") 获取编码规范，实现代码必须遵守
- 调用 Skill("<lang>-testing") 获取测试规范，测试代码必须遵守
- 调用 Skill("<lang>-error-handling") 获取错误处理规范，错误处理必须遵守
（将 <lang> 替换为实际技术栈对应的 skill 前缀，如 golang/java/python/nodejs 等）

Skill 返回的规范是你的实现约束，优先级高于下方默认流程。
```

> **为什么必须这样写**：subagent 运行在独立上下文中，不继承主 session 的 skill 记忆。
> 仅写"遵守编码规范"无效——subagent 不知道有哪些 skill 可用，也不会主动调用。
> 必须在 prompt 中给出具体 skill 名称 + 明确的 `Skill("xxx")` 调用指令。

### subagent 执行流程

```
1. 按 prompt 指令依次调用 Skill 工具，加载所有强制 skill 的规范内容
2. 按 skill 规范 + Task 协议执行（skill 规范优先级高于下方默认流程）
3. 若无相关 skill 或 skill 未覆盖，执行默认流程：
   a. 阅读 Task 协议的 P2 接口约束
   b. 先写测试（基于测试策略的用例）
   c. 运行测试 → 确认红灯
   d. 实现代码（严格遵守接口签名 + 实现协议）
   e. 运行测试 → 确认绿灯
   f. 补充注释：公开方法加头部注释，复杂逻辑块加行内注释，只写为什么这样做
   g. 自检：代码是否与 P2 接口一致？是否遵守 ADR？
   h. build + test 全量通过后报告完成
```

### subagent 铁律

| 规则 | 说明 |
|---|---|
| 文件隔离 | 只能修改本 Task 声明的目标文件 |
| 接口锁定 | P2 签名不可变，发现需改必须暂停上报 |
| 测试先行 | 先写测试再实现，禁止跳过 |
| 编码规范 | 必须通过 Skill 工具触发已安装的编码/TDD skill，不可仅口头遵守 |
| 注释完善 | 公开方法必须有头部注释；复杂逻辑块必须有行内注释；只写 WHY 不写 WHAT |
| 独立验证 | 完成后运行 build + test |

### 串行 Task

前一个 Task 通过验证后，再派发下一个。

### 无法并行时

必须说明退化原因。

## Phase E: 集成验证（三闸，缺一不可）

1. **产物存在闸**：`node ${CLAUDE_PLUGIN_ROOT}/scripts/sdd.mjs verify-artifacts SDD/contracts/<name>/P3-impl-<name>.md`
   每个 Task 声明的 file:/test: 必须真实存在且非空，红则补齐缺失文件后重跑。
2. **产物正确闸**：跑项目级测试命令（根据 P2 技术栈确定，如 Go: `go test ./...`、Java: `mvn test`、Node: `npm test`、Python: `pytest`），失败则修实现。
3. **契约闸**：`node ${CLAUDE_PLUGIN_ROOT}/scripts/sdd.mjs gate SDD/contracts/<name>/P3-impl-<name>.md`
   校验 P2 每个 IU 都被 Task 覆盖 + 每 Task 字段完整。

---

## Phase F: P2 一致性复核

三闸通过后，逐个检查：
- 每个已实现的函数签名是否与 P2 接口定义完全一致（参数名、类型、返回值）
- 每个数据模型字段是否与 P2 定义一致
- ADR 决策是否被正确落地（如选了责任链就不能写成 if-else）
- 扩展点接口是否已实现并可注册新实现

不一致项必须修复后重跑三闸。

---

## Phase G: 确认

三闸全绿 + P2 一致性复核通过后展示实现摘要（新增/修改文件数、测试结果、构建状态、P2 一致性状态），等用户明确确认"进入 P4"。不得自动推进。
用户确认后运行 `node ${CLAUDE_PLUGIN_ROOT}/scripts/sdd.mjs state-set <name> P3 confirmed true` 落盘确认状态（P4 的 can-enter 据此放行）。

---

## 硬约束

1. **Task 必须是完整协议** — 禁止只写文件名+一句话完成标准；每个 Task 必须含接口约束、实现协议、测试策略
2. **subagent 不得修改非本 Task 文件** — 文件隔离是铁律
3. **P2 接口签名不可变** — 发现接口需改必须回退到 P2
4. **不得自动推进** — 三闸未全绿不得请求用户确认
5. **依赖不明确时按串行** — 宁可慢不可错
6. **集成验证必须全量** — 不能只跑被改文件的测试
7. **P3 必须 100% 覆盖 P2 所有 IU，gate coverage 红绝不可绕过**
8. **代码必须与 P2 完全一致** — 函数签名、数据模型、ADR 决策不可偏离
9. **必须通过 Skill 工具触发已安装 skill** — subagent prompt 中必须包含明确的 Skill 工具调用指令，仅文字描述"遵守规范"无效
10. **关键逻辑必须有注释** — 公开方法有头部注释；复杂逻辑块有行内注释；只写 WHY，禁止废话注释（如 "// 返回结果"）
