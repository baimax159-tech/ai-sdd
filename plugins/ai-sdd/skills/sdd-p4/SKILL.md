# P4 验证执行引擎

## 触发条件

- P3 已确认（三闸全绿 + 用户确认）
- 用户确认开始验证

## Phase A: 加载验证源

0. **前置硬闸**：运行 `node ${CLAUDE_PLUGIN_ROOT}/scripts/sdd.mjs can-enter <name> P4`。
   非 0 退出（P3 gate 未绿或未经用户确认）则拒绝进入，提示用户先完成并确认 P3，不得继续。
1. 从 P1-req 提取：AC、AC-FAIL、NFR
2. 或从 P1p-diff 提取：DF 差异项、行为一致性声明
3. 从 P2 提取：可验证架构约束、验证命令
4. 确认范围："本次验证覆盖以下条目，有遗漏吗？"

**上下文聚焦**：验证源已加载完毕。本阶段所有判断和产出以上方 P1/P2/P3 契约的明文内容为唯一信息基准，不依赖对话历史中的隐含假设或推断；遇到模糊或信息缺失，以契约文件为准，契约未覆盖的事项用 AskUserQuestion 向用户确认。

---

## Phase B: 生成验证覆盖矩阵

逐条匹配：

| P1 条目 | 验证场景 | 验证方式 | 通过判据 |
|---|---|---|---|
| AC-01 | 正常路径测试 | 集成测试 / E2E | 预期输出匹配 |
| AC-FAIL-01 | 异常路径测试 | 单元测试 | 错误码正确 |
| NFR-01 | 性能测试 | benchmark | P99 < 阈值 |
| DF-01 | 行为比对 | diff | 业务字段 100% 一致 |

**规则：**
- 每条 AC/DF 至少一个验证场景
- 每个验证场景必须有可执行的验证命令和数值化通过判据
- 未覆盖项必须说明原因或标注风险接受

展示矩阵 → 用户确认

---

## Phase C: 执行验证

### 独立场景可并行（subagent）

按验证类型分组：
- subagent-1：功能验证（AC 正向场景）
- subagent-2：异常验证（AC-FAIL 场景）
- subagent-3：性能验证（NFR 场景）
- subagent-4：兼容验证（DF 一致性比对）

每个 subagent：
- 执行分配的验证命令
- 记录结果（pass/fail + 实际值）
- 失败时提供错误定位信息

### 不可并行的验证

- 有状态依赖的场景（A 的结果是 B 的前置）→ 串行
- 需要共享环境的（同一数据库状态）→ 串行

---

## Phase D: 结果汇总

1. 收集所有验证结果
2. 更新覆盖矩阵（标注 pass/fail + 实际值）
3. 全部通过 → Phase E
4. 有失败项：
   - 展示失败详情
   - 定位问题根因
   - 修复 → 重新验证失败项
   - 修复后再跑一次全量回归确认无副作用

---

## Phase E: 业务可用性验收

**目的**：单元/集成测试只验证"代码正确"，本阶段验证"业务可用"——用真实场景端到端跑通，发现 mock 掩盖的集成缺陷。

### E-1: 确定服务类型与验收策略

使用 `AskUserQuestion` 确认项目类型：

| 项目类型 | 验收策略 |
|---|---|
| Web 服务（HTTP API） | 启动服务 → 发真实请求 → 断言响应 + 副作用 |
| Web 前端 | 启动 dev server → 引导用户手动走查关键路径 |
| CLI 工具 | 执行完整命令序列 → 断言输出 + 文件/状态变化 |
| 库/SDK | 编写调用示例 → 真实运行 → 断言结果 |
| 数据管道/批处理 | 用真实数据样本跑一遍 → 断言产出 |

### E-2: 构建业务场景用例

从 P1 AC 逐条反推**端到端业务场景**（非单元测试级别）：

每个场景必须包含：
- **前置条件**：数据库状态 / 依赖服务状态 / 配置
- **操作步骤**：完整的用户操作序列（不是单个函数调用）
- **预期结果**：响应内容 + 数据库变化 + 副作用（消息、事件、文件等）
- **对应 AC 编号**：追溯到 P1 需求

**Web 服务场景模板**：
```
场景：<业务动作描述>
前置：<数据准备、服务状态>
请求：<method> <path> + body/headers
断言：
  - HTTP status = <期望码>
  - response body 含 <关键字段>
  - DB 表 <table> 新增/更新了 <预期记录>
  - （如有）下游事件/消息已发送
覆盖：AC-XX, AC-XX
```

**规则**：
- 每条核心 AC 至少对应一个端到端场景
- 场景必须覆盖完整业务链路，不得只测单个接口隔离行为
- 有状态依赖的场景按依赖顺序编排（如：先注册 → 再登录 → 再操作）

展示场景列表 → 用户确认

### E-3: 执行端到端验收

**Web 服务**：
1. 启动服务（`Bash` 执行项目的启动命令，如 `go run`、`mvn spring-boot:run`、`npm start`）
2. 等待服务就绪（轮询健康检查端点或端口）
3. 按场景顺序发送真实 HTTP 请求（`curl` / `httpie`）
4. 断言响应状态码、body 关键字段
5. 检查数据库/文件等副作用（如适用）
6. 记录每个场景 pass/fail + 实际响应

**非 Web 项目**：
1. 准备真实输入数据（非 mock）
2. 执行完整业务流程命令
3. 断言输出和状态变化

**无法自动验收时**（如依赖外部服务、需要 UI 操作）：
- 生成可执行的验收脚本交付用户
- 明确标注"需人工执行"并列出操作步骤
- 用 `AskUserQuestion` 让用户确认执行结果

### E-4: 可用性缺陷修复

发现的问题分两类处置：

| 缺陷类型 | 处置 |
|---|---|
| 代码逻辑缺陷（接口行为不符预期） | 修复代码 → 重跑 Phase C + E 全量 |
| 集成缺陷（服务间交互、配置、环境） | 修复配置/集成代码 → 重跑 Phase E |
| 需求理解偏差（AC 本身有歧义） | 暂停，追问用户澄清后修复 |

**修复后必须全量回归**（Phase C 的单元测试 + Phase E 的端到端场景全部重跑）。

---

## Phase F: 最终确认

1. 展示验证覆盖矩阵（全绿）
2. 展示业务可用性验收结果（全绿）
3. 运行契约闸：`node ${CLAUDE_PLUGIN_ROOT}/scripts/sdd.mjs gate SDD/contracts/<name>/P4-verify-<name>.md`
4. 展示最终摘要：
   ```
   "P4 验证完成:
    - AC 覆盖: X/X pass
    - AC-FAIL 覆盖: Y/Y pass
    - NFR 覆盖: Z/Z pass
    - 架构约束: W/W pass
    - 业务可用性: M/M pass（N 个端到端场景全部通过）
    - gate: pass"
   ```
5. gate 绿后展示摘要，停下等用户确认。
6. 等用户确认后运行 `node ${CLAUDE_PLUGIN_ROOT}/scripts/sdd.mjs state-set <name> P4 confirmed true` 落盘确认状态，再引导进入 P5。不得自动推进。
7. **引导下一步**："P4 验证通过，是否进入 P5 沉淀开发规则？（推荐：将本次实现经验转化为项目规则，提升后续开发质量）"

---

## Phase G: 回滚预案（确认前必须有）

P4 契约必须包含回滚预案：
- 验证失败时的处置步骤
- 部署后发现问题的回退方案
- 数据迁移场景的回滚策略

追问："如果验证后上线发现问题，回退方案是什么？"

---

## 硬约束

1. **每条 AC/DF 必须有验证场景** — 不得遗漏
2. **通过判据必须数值化** — "运行正常"不算通过判据
3. **验证命令必须可执行** — 不接受"人工检查"
4. **失败修复后必须全量回归** — 不能只重跑失败项
5. **不得自动推进** — gate 未绿不得请求用户确认
6. **回滚预案不可为空** — 必须有具体步骤
7. **业务可用性验收不可跳过** — 单元测试全绿不等于业务可用，必须执行端到端场景验证
8. **端到端场景必须用真实请求** — 禁止用 mock/stub 替代真实服务调用；无法自动化时必须生成脚本并标注"需人工执行"
9. **可用性修复后必须双重回归** — 单元测试 + 端到端场景全部重跑
