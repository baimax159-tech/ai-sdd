# P5 开发规则沉淀引擎

## 触发条件

- P4 全链路已确认完成
- 用户确认开始规则沉淀

## Phase A: 加载全链路产物

1. 读取本次 SDD 全部契约：
   - P1 需求契约（AC/NFR/技术约束）
   - P2 架构契约（ADR、模块划分、接口定义、通用抽象）
   - P3 实现契约（Task 协议、实现策略）
   - P4 验证契约（验证发现、修复记录）
2. 扫描本次产出的代码文件，用 CodeGraph 分析：
   - `codegraph_files` 确认新增/修改文件范围
   - `codegraph_context` 获取实现的整体结构
   - `codegraph_callers`/`codegraph_callees` 确认模块间交互模式
3. 读取项目现有规则（如 `.claude/rules/`、`CLAUDE.md`），避免重复

---

## Phase B: 提炼规则候选项

从以下维度提炼本次实现中值得沉淀的规则：

### B-1: 架构模式规则

从 P2 ADR 和实际实现中提取：
- 模块分层约定（如"domain 层不依赖 infra 层"）
- 依赖方向约束（如"handler → service → repo，禁止反向"）
- 接口设计范式（如"所有 API 返回统一 Response 包装"）
- 错误处理模式（如"业务错误用错误码，系统错误用 panic/exception"）

### B-2: 编码规范规则

从 P3 实现代码中提取：
- 命名约定（包/类/方法/变量的命名模式）
- 文件组织约定（如"每个聚合根一个目录"）
- 测试约定（如"表驱动测试、mock 策略、fixture 管理"）
- 注释约定（如"接口必须有 doc comment，内部实现只注释 why"）

### B-3: 框架使用规则

从实际代码中提取框架/库的使用模式：
- 框架初始化模式（如"Spring Boot 用 @Configuration + @Bean"）
- 中间件/拦截器使用约定
- ORM/数据库访问模式
- 配置管理方式

### B-4: 质量保障规则

从 P4 验证过程中提取：
- 哪些测试模式有效发现了 bug
- 哪些集成测试策略值得复用
- 哪些验证步骤应标准化

### B-5: 踩坑记录

从修复过程中提取：
- P3/P4 修复的典型问题 → 转化为"避免规则"
- 验证失败的根因 → 转化为编码检查项

---

## Phase C: 用户确认与筛选

展示所有候选规则 → 用户逐条 triage：

使用 `AskUserQuestion` 逐组确认：
- **采纳** — 写入项目规则
- **修改** — 用户调整措辞后采纳
- **丢弃** — 本次不沉淀（过于特殊 / 不具通用性）

**规则**：
- 只沉淀**通用性强**的规则（后续功能大概率会复用）
- 不沉淀业务逻辑细节（那是代码和注释的职责）
- 每条规则必须可操作（有明确的"做/不做"指引）

---

## Phase D: 写入规则文件

### D-1: 确定写入位置

按项目现有结构选择：

| 项目有 | 写入位置 |
|---|---|
| `.claude/rules/project/` 目录 | 在该目录新建或追加规则文件 |
| `CLAUDE.md` | 在适当章节追加规则 |
| 两者都有 | 细粒度规则写 `rules/`，概要写 `CLAUDE.md` |
| 都没有 | 创建 `.claude/rules/project/dev-rules.md` |

### D-2: 规则文件格式

```markdown
# <模块/领域> 开发规则

> 由 SDD P5 从 <name> 功能实现中沉淀，<日期>

## 架构约束

- <规则1>：<说明>
- <规则2>：<说明>

## 编码规范

- <规则1>：<说明>
- <规则2>：<说明>

## 框架使用

- <规则1>：<说明>

## 禁止事项

- <规则1>：<原因>
```

### D-3: 规则合并策略

写入前必须逐条对比已有规则，按关系类型处理：

| 关系 | 判断标准 | 处理方式 |
|---|---|---|
| **重复** | 新旧规则说的是同一件事，措辞不同 | 跳过新规则，保留已有 |
| **升级** | 新规则是旧规则的精确化/细化版本 | 用新规则替换旧规则，标注 `<!-- upgraded from: ... -->` |
| **互补** | 两条规则覆盖同一领域的不同侧面 | 合并为一条更完整的规则 |
| **冲突** | 新旧规则互相矛盾 | 暂停，展示冲突对比，用 `AskUserQuestion` 让用户选择保留哪条或如何调和 |
| **独立** | 与已有规则无关 | 正常追加 |

**合并流程**：

1. 用 `Read` 加载目标规则文件全部内容
2. 逐条新规则，在已有规则中查找**语义相近项**（同一领域 + 同一约束对象）
3. 找到相近项 → 判断关系类型（重复/升级/互补/冲突）
4. 展示合并计划给用户确认：
   ```
   "规则合并计划：
    - 新增 3 条（无冲突）
    - 升级 1 条：旧 'xxx' → 新 'yyy'（更精确）
    - 合并 1 条：'aaa' + 'bbb' → 'ccc'
    - 冲突 1 条：需要你决定（见下方）
    - 跳过 2 条（与已有重复）"
   ```
5. 用户确认后执行写入

**冲突展示格式**：
```
冲突：关于 <领域>
  已有规则：<原文>（来源：SDD/xxx）
  新规则：  <原文>（来源：SDD/yyy）
  请选择：A) 保留已有  B) 替换为新  C) 合并为：<建议合并文本>
```

### D-4: 执行写入

- **新增**：用 `Edit` 在对应章节末尾追加
- **升级**：用 `Edit` 替换原规则行，保留来源注释
- **合并**：用 `Edit` 替换原规则行为合并后的新文本
- **冲突**：按用户决策执行
- 每条规则标注来源（`<!-- from: SDD/<name> -->`）

---

## Phase E: 验证与确认

1. 读取写入后的规则文件，确认格式正确
2. 检查规则是否与 `CLAUDE.md` 或其他规则文件冲突
3. 展示最终写入摘要：
   ```
   "P5 规则沉淀完成:
    - 架构规则: N 条
    - 编码规范: N 条
    - 框架使用: N 条
    - 禁止事项: N 条
    - 写入文件: <path>
    全链路 P1→P5 完成。"
   ```
4. 等用户确认。不得自动推进。

---

## 硬约束

1. **不得跳过用户确认** — 每条规则必须经用户 triage
2. **规则必须可操作** — 禁止写"注意代码质量"这类空话，必须有具体做/不做指引
3. **不沉淀业务逻辑** — 规则是框架级/模式级的，不是"用户表有 email 字段"这种
4. **增量不覆盖** — 追加规则不得删除已有规则（升级/合并除外，且必须用户确认）
5. **标注来源** — 每条规则标注从哪个 SDD 功能沉淀
6. **不重复** — 与已有规则语义重复的直接跳过
7. **冲突必须仲裁** — 新旧规则矛盾时必须暂停让用户决策，不得静默覆盖
8. **合并计划必须展示** — 写入前必须向用户展示完整的合并计划（新增/升级/合并/冲突/跳过），确认后才执行
